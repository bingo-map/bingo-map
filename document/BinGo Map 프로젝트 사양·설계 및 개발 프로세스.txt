## 1. 기안: 무엇을 만들 것인가

### 1.1 프로젝트 제안

BinGo Map(Clean & Gourmet)은 일본 오사카 여행자가 테이크아웃 맛집을 찾고, 지도에서 쓰레기통과 경로를 확인해 여행 후 쓰레기까지 편하게 처리하도록 돕는 웹 서비스입니다.

### 1.2 해결하려는 문제

여행자가 길거리 음식을 즐긴 뒤 가까운 쓰레기통을 찾기 어렵고, 맛집 정보와 쓰레기 처리 장소가 서로 다른 서비스에 흩어져 있습니다. BinGo Map은 맛집 탐색, 이동, 쓰레기통 확인을 한 서비스 흐름으로 연결하고 리뷰·제보·커뮤니티로 정보를 보완합니다.

### 1.3 목표 사용자와 제공 가치

| 사용자 | 필요한 일 | 제공 가치 |
|---|---|---|
| 오사카 여행자 | 주변 맛집과 쓰레기통 탐색, 경로 확인 | 음식점부터 쓰레기 처리 장소까지 이어지는 지도 경험 |
| 회원 | 리뷰·제보·게시글 작성, 정보 저장 | 여행 정보를 다시 찾고 다른 여행자와 공유 |
| 관리자 | 제보 검수, 공지·회원·서비스 관리 | 사용자 정보와 운영 상태 관리 |

## 2. 요건 정의: 어떤 제품을 만들었는가

### 2.1 핵심 사용 시나리오

1. 여행자는 지도나 주변 맛집 목록에서 식당을 찾습니다.
2. 상세 화면에서 메뉴, 위치, 영업 정보와 리뷰를 확인합니다.
3. 맛집을 즐겨찾기에 저장하고 도보·자전거·자동차 경로를 조회합니다.
4. 식사 후 지도에서 가까운 쓰레기통을 확인합니다.
5. 위치가 잘못되었거나 누락됐다면 회원 제보를 등록합니다.
6. 관리자는 제보를 검토하고 승인된 쓰레기통 정보를 지도에 반영합니다.

### 2.2 기능 요구사항

| ID | 요구사항 | 현재 상태 |
|---|---|---|
| FR-01 | 도시별 쓰레기통을 지도에서 확인하고 위치 정보를 조회한다. | 구현 확인 |
| FR-02 | 지역별 맛집 목록과 상세·메뉴 정보를 조회한다. | 구현 확인 |
| FR-03 | 식당 주변 추천과 맛집 공개 상태를 제공한다. | 구현 확인 |
| FR-04 | 출발지·목적지와 이동 수단으로 경로를 조회한다. | 구현 확인 |
| FR-05 | 가입·로그인·로그아웃 및 사용자 세션을 처리한다. | 구현 확인 |

| FR-09 | 쓰레기통 제보 등록·조회와 관리자 검수 기능을 제공한다. | 구현 확인 |
| FR-10 | 마이페이지에서 사용자 정보와 작성 활동을 확인한다. | 구현 확인 |
| FR-11 | 관리자 공지·회원·알림·서비스 설정을 지원한다. | 구현 확인 |

### 2.3 비기능 요구사항 및 제약

- **응답 구조:** 화면은 HTML/CSS/JavaScript로 제공하고, 비동기 기능은 JSON API를 사용합니다.
- **접근 제어:** 로그인 세션과 역할에 따라 사용자·관리자 기능을 제한합니다.
- **데이터 일관성:** Oracle 테이블과 애플리케이션 Entity·SQL 간 컬럼 및 시퀀스 구성을 일치시킵니다.
- **외부 의존성:** 지도 타일·지도 데이터·경로 계산은 외부 서비스 정책과 네트워크에 영향을 받습니다.
- **실행 환경:** Java 17, Spring Boot 4.1.1, Gradle Wrapper, Oracle Database를 사용합니다.
- **검증 한계:** 저장소에서 확인되는 자동 테스트는 제한적이므로 전체 기능의 자동 검증 완료를 주장하지 않습니다.

### 2.4 범위 결정

**핵심 흐름:** 맛집 탐색 → 상세 확인 → 경로 조회 → 쓰레기통 탐색.

**지원 흐름:** 회원·즐겨찾기·리뷰·제보·커뮤니티.

**운영 흐름:** 관리자 검수·공지·회원 관리·알림·서비스 설정.

초기 제안에 있던 소셜 로그인, 메일 발송 방식 비밀번호 재설정, 결제 등은 현재 구현된 기능으로 간주하지 않습니다. 기능 범위가 넓어진 만큼 발표에서는 핵심 여행 흐름과 운영 지원 기능을 나누어 설명하는 것이 적절합니다.

## 3. 기본 설계: 전체 구성을 어떻게 나눴는가

### 3.1 기술 선택

| 영역 | 선택 | 프로젝트에서의 역할 |
|---|---|---|
| 백엔드 | Java 17, Spring Boot 4.1.1, Spring MVC | 화면 라우팅과 REST API 제공 |
| 데이터 | Oracle 11g 호환 스키마, Spring Data JPA | 회원·맛집·리뷰·커뮤니티 등 저장 |
| 지도 데이터 조회 | JdbcTemplate 및 저장된 DB 데이터 | 쓰레기통 지도 데이터 조회 |
| 프런트엔드 | HTML, CSS, Vanilla JavaScript | 화면 구성과 API 연동 |
| 지도 | Leaflet, OpenStreetMap | 지도 표시와 마커·경로 시각화 |
| 경로 | 공개 OSRM 호환 경로 서버 | 이동 수단별 경로 및 안내 조회 |
| 빌드 | Gradle Wrapper | 일관된 프로젝트 빌드·실행 |

이 구성은 하나의 Spring Boot 애플리케이션에서 기능을 모듈별로 관리하는 모놀리스입니다. 현재 코드의 규모와 팀 프로젝트 통합 방식에 맞춰 기능 경계를 패키지로 나눴습니다.

### 3.2 시스템 아키텍처

```text
┌─────────────────────────────────────────────┐
│ 브라우저                                     │
│ HTML / CSS / Vanilla JS / Leaflet            │
└──────────────────────┬──────────────────────┘
                       │ 페이지 요청 / fetch(JSON)
                       ▼
┌─────────────────────────────────────────────┐
│ Spring MVC                                   │
│ 화면 Controller / REST Controller            │
│ 기능별 Service / Repository / DTO             │
└──────────────┬──────────────────┬───────────┘
               │                  │ 경로 요청
               ▼                  ▼
       ┌──────────────┐   ┌────────────────────┐
       │ Oracle DB    │   │ 공개 경로 서버     │
       │ 도메인 데이터│   │ OSRM 호환 서비스   │
       └──────────────┘   └────────────────────┘
```

### 3.3 백엔드 모듈 경계

| 패키지 | 책임 |
|---|---|
| `common` | 웹 설정 및 서비스 운영 설정 |
| `community` | 게시글·댓글·좋아요·태그 |
| `entity` | 공통 감사 필드 및 즐겨찾기 대상 타입 |
| `favorite` | 즐겨찾기 등록·조회·삭제 |
| `map` | 쓰레기통 조회 및 지도 화면 |
| `notice` | 공지 조회 및 관리자 관리 |
| `notification` | 알림 조회·읽음·삭제 |
| `report` | 쓰레기통 제보 및 관리자 검수 |
| `restaurant` | 맛집·메뉴·추천·공개 상태 |
| `restaurantmap` | 지도 화면용 맛집 조회 |
| `review` | 리뷰·사진·도움 표시 |
| `routing` | 경로 API와 외부 경로 서버 연동 |
| `user` | 가입·로그인·세션·마이페이지·비밀번호 재설정 |
| `user.admin` | 관리자 대시보드 및 회원 관리 |

페이지 라우팅과 JSON API는 코드에서 함께 다룹니다. Controller가 도메인별로 구성되어 있어 화면/API 분리 방식은 모듈마다 다를 수 있습니다.

### 3.4 데이터 설계 개요

아래는 Entity와 SQL 파일에서 확인되는 주요 데이터 그룹입니다. 전체 컬럼·타입·인덱스·시퀀스는 `DB/`의 팀 SQL 및 Entity 매핑을 확인해야 합니다.

| 데이터 그룹 | 주요 테이블 | 관계/용도 |
|---|---|---|
| 회원 | `users` | 계정, 역할, 사용자 설정 및 차단 상태 |
| 맛집·메뉴 | `RESTAURANTS`, `restaurant_menu` | 식당 상세, 좌표, 공개 상태와 메뉴 |
| 쓰레기통 | `waste_bin` | 도시·좌표·종류·주소를 가진 지도 데이터 |
| 즐겨찾기 | `favorites` | 사용자와 대상 종류·ID를 연결 |
| 리뷰 | `reviews`, `review_image` | 작성자, 대상 식당, 리뷰 사진과 도움 수 |
| 커뮤니티 | `community_post`, `community_comment`, `community_post_like` | 게시글·댓글·좋아요 |
| 제보 | `bin_reports` | 제보 위치와 승인·반려·보류 상태 |
| 운영 | `notices`, `notifications`, `system_settings` | 공지·알림·서비스 설정 |

맛집과 쓰레기통 즐겨찾기는 `target_type` 및 `target_id`로 대상을 구분합니다. 쓰레기통은 현재 DB 테이블에서 읽으므로 “테이블 없이 Overpass에서 매번 조회한다”는 초기 설계 설명은 폐기합니다. 모든 Entity가 `BaseEntity`를 상속한다는 초기 규칙도 실제 코드와 다르므로 공통 규칙으로 두지 않습니다.

## 4. 상세 설계: 대표 흐름을 어떻게 처리하는가

### 4.1 맛집 탐색부터 쓰레기통 확인까지

```text
여행자       브라우저/Leaflet        Spring API/Service         Oracle       경로 서버
  │                 │                       │                    │              │
  │ 맛집 목록 요청   │                       │                    │              │
  ├────────────────>│ GET /api/restaurants  │                    │              │
  │                 ├──────────────────────>│ 공개 맛집 조회     │              │
  │                 │                       ├───────────────────>│              │
  │                 │                       │<───────────────────┤              │
  │                 │<──────────────────────┤ JSON 목록          │              │
  │ 상세·경로 선택   │                       │                    │              │
  ├────────────────>│ POST /api/routes      │                    │              │
  │                 ├──────────────────────>│ 좌표·수단 검증     │              │
  │                 │                       ├─────────────────────────────────>│
  │                 │                       │<─────────────────────────────────┤
  │                 │<──────────────────────┤ 경로·단계 안내     │              │
  │ 쓰레기통 조회    │                       │                    │              │
  ├────────────────>│ GET /api/bins         │                    │              │
  │                 ├──────────────────────>│ 도시별 데이터 조회 │              │
  │                 │                       ├───────────────────>│              │
  │                 │                       │<───────────────────┤              │
  │                 │<──────────────────────┤ JSON 마커 데이터   │              │
  │                 │ 지도에 경로·마커 표시 │                    │              │
```

### 4.2 주요 처리 규칙

#### 경로 조회

- 요청에는 출발·도착 위도/경도와 이동 수단을 사용합니다.
- 이동 수단은 `walk`, `bike`, `car` 중 하나여야 합니다.
- 좌표 범위와 최대 직선거리(50km)를 확인하고 잘못된 요청은 오류 응답으로 종료합니다.
- 공개 경로 서버에 요청하고 결과 좌표·거리·시간·단계 안내를 화면에서 쓰는 응답으로 변환합니다.
- 동일 요청은 메모리 캐시를 사용하며 공개 서버의 요청 제한 응답도 처리합니다.

#### 쓰레기통 제보

```text
회원 ── 제보 등록 ──> 대기 제보 저장
                         │
                         ▼
관리자 검수 ── 승인 ──> 쓰레기통 지도 데이터 반영 ──> 사용자 알림
       ├────── 반려 ──> 반려 사유 저장 및 알림
       └────── 보류 ──> 검수 상태 갱신
```

제보 API와 검수 API의 권한, 상태값, 요청 필드는 `report/BinReportController.java` 및 `report/AdminReportController.java`를 기준으로 합니다.

### 4.3 주요 API 계약(요약)

| 기능 | 경로 요약 |
|---|---|
| 맛집 | `GET /api/restaurants`, `/popular`, `/{id}`, `/{id}/nearby`, `/{id}/menu`; 공개·비공개 변경 `POST /{id}/publish`, `/unpublish` |
| 지도 | `GET /api/bins`, `/api/map/restaurants`, `/api/reports/approved` |
| 경로 | `POST /api/routes` |
| 즐겨찾기 | `GET /api/favorites`, `/status`; `POST /api/favorites`; `DELETE /api/favorites/{id}` |
| 리뷰 | `/api/reviews` 목록·상세·작성·수정·삭제·도움 및 식당별 조회 |
| 커뮤니티 | `/api/community` 게시글 CRUD, 태그·좋아요·댓글 |
| 사용자 | `/signup`, `/login`, `/logout`, `/api/session`, `/api/mypage/*`, `/api/password-reset/*` |
| 제보·관리 | `/api/reports/*`, `/api/admin/reports/*`, `/api/admin/users/*` |
| 공지·알림 | `/api/notices/*`, `/api/admin/notices/*`, `/api/notifications/*` |
| 운영 설정 | `/api/settings/public`, `/api/admin/settings` |

전체 메서드·파라미터·응답·권한 조건은 Controller의 실제 매핑과 DTO에서 확인합니다. 이 문서는 API의 완전한 OpenAPI 명세가 아닙니다.

| 사용자·관리자 | `user/`, `user/admin/`, `static/login/`, `signup/`, `mypage/`, `admin/` |
| 즐겨찾기 | `favorite/`, `static/favorites/` |
| 리뷰 | `review/`, `static/reviews/` |
| 커뮤니티 | `community/`, `static/community/` |
| 제보·검수 | `report/`, `static/report/` |
| 공지·알림 | `notice/`, `notification/`, 관련 정적 화면 및 공통 JS |
| 데이터베이스 스크립트 | `DB/` |

### 5.2 구현 시 유지할 경계

- 새 기능은 기존의 기능별 패키지와 화면 디렉터리 구조에 맞춥니다.
- 화면 입력값만 신뢰하지 않고 Controller/Service에서 유효성·소유권·역할을 검증합니다.
- DB 변경은 Entity만으로 자동 반영되지 않으므로 Oracle SQL과 함께 검토합니다 (`ddl-auto: none`).
- 외부 경로 서버 장애·요청 제한은 사용자에게 이해 가능한 실패 응답으로 전달합니다.
- 팀원별 구현 기여는 저장소 README의 Team 섹션과 커밋/PR 근거를 함께 참고합니다.

## 6. 테스트: 무엇을 확인했고 무엇이 남았는가

### 6.1 현재 저장소에서 확인되는 근거

자동 테스트 소스에는 Spring 애플리케이션 컨텍스트 로딩 테스트가 확인됩니다. 도메인별 API·권한·Oracle 통합·외부 경로 서버 테스트가 충분히 갖춰졌다고 볼 근거는 제한적입니다. 이 문서는 테스트를 실행했다고 주장하지 않습니다.

### 6.2 권장 검증 시나리오

| 영역 | 정상 흐름 | 경계·실패 흐름 |
|---|---|---|
| 회원 | 가입, 로그인, 세션 확인, 로그아웃 | 중복 이메일, 잘못된 비밀번호, 비로그인 접근 |
| 권한 | 관리자 기능의 허용 역할 접근 | 일반 사용자 접근, 차단 사용자 요청 |
| 맛집 | 공개 식당 목록·상세·주변 추천 | 비공개 식당, 존재하지 않는 ID, 좌표 누락 |
| 즐겨찾기·리뷰 | 저장·조회·삭제, 리뷰 CRUD | 중복 저장, 타인 데이터 수정·삭제 |
| 제보 | 등록 후 승인되어 지도 반영 | 반려·보류, 잘못된 좌표, 권한 없는 검수 |
| 경로 | 이동 수단별 경로 조회 | 잘못된 좌표·수단, 무경로, 외부 서버 지연·429 |
| Oracle | 실제 스키마에서 CRUD 확인 | 누락 테이블·시퀀스·컬럼 및 타입 불일치 |

### 6.3 향후 테스트 보완 우선순위

1. 서비스 단위 테스트: 상태 전이, 거리 계산, 권한·소유권 규칙.
2. MockMvc API 테스트: 정상 요청, 입력 오류, 인증·권한 응답.
3. 테스트 DB 통합 테스트: 팀 Oracle 스키마와 제약을 재현할 수 있는 환경 구성.
4. 경로 서버 응답은 외부 네트워크 대신 모의 응답으로 검증하고, 수동 연결 확인을 별도로 기록.

## 7. 릴리즈: 실행 및 배포 고려사항

### 7.1 로컬 실행

- 요구 환경: Java 17, Oracle Database 및 프로젝트 스키마
- 설정: `src/main/resources/application.yaml`의 JDBC 연결을 로컬 환경에 맞게 지정
- 실행: `./gradlew bootRun` 또는 Windows의 `gradlew.bat bootRun`
- 접속: `http://localhost:8080`

접속 정보는 환경별로 관리하고 공개 저장소에 비밀번호를 커밋하지 않습니다. `ddl-auto: none`이므로 사전에 팀 SQL로 데이터베이스를 준비해야 합니다.

### 7.2 배포 준비 체크리스트

- [ ] 운영 DB 접속 정보와 비밀값을 환경 변수·비밀 저장소로 분리
- [ ] 운영 Oracle 스키마·시퀀스·인덱스 적용 및 백업 확인
- [ ] 공개 OSRM 호환 서버의 사용 정책·요청량·장애 대안 결정
- [ ] 업로드 파일의 영속 저장 경로와 접근 정책 결정
- [ ] 운영 프로필, 로그, 오류 응답, 관리자 계정 초기화 절차 확인
- [ ] 핵심 API 및 권한 시나리오 테스트 결과 기록
- [ ] 배포와 롤백 절차를 정하고 실제 배포 결과 기록

AWS 배포, 고가용성(HA), 실제 운영 배포는 이 문서의 작성 시점에 구현 완료로 확인된 기능이 아닙니다. 향후 목표로 구분해 관리합니다.

## 8. 개발 프로세스와 AI 활용 원칙

### 8.1 팀이 적용할 개발 흐름

```text
기안
  ↓ 목적·문제·대상 사용자 합의
요건 정의
  ↓ 기능 범위·우선순위·완료 조건 작성
기본 설계
  ↓ 화면 흐름·모듈 경계·데이터 관계·API 초안 검토
상세 설계
  ↓ 대표 시퀀스·예외 흐름·권한·DB 변경 구체화
구현
  ↓ 기능 브랜치에서 설계에 맞게 개발
테스트
  ↓ 단위·API·통합·수동 검증 및 결과 기록
릴리즈
  ↓ 배포·운영 확인·롤백 방법 기록
```

기능을 추가하거나 크게 수정할 때는 이 흐름을 작은 단위로 반복합니다. 모든 변경이 문서 작성 뒤에만 가능하다는 절대 규칙이 아니라, 변경 위험과 범위에 맞게 설계와 검증을 남기는 협업 기준입니다.

### 8.2 AI 사용 원칙

- AI는 사양서·설계 초안, 코드 탐색, 오류 원인 후보, 반복 작업을 보조할 수 있습니다.
- 팀원은 AI 초안을 직접 검토하고 시스템 구조와 선택 이유를 설명할 책임이 있습니다.
- AI가 만든 코드·문서가 저장소에 반영됐다는 사실만으로 이해·검증이 완료된 것으로 간주하지 않습니다.
- AI 제안은 실제 코드, DB 스키마, 외부 서비스 정책과 대조하고 검증 결과를 기록합니다.
- 포트폴리오에서는 본인의 구현, 팀 협업, AI 보조 범위를 구분해 설명합니다.

### 8.3 발표·면접에서의 설명 기준

프로젝트 전체 기능과 개인 담당 기능을 분리합니다. 본인이 직접 맡은 기능은 목적, 설계 선택, 데이터/API 흐름, 발생한 문제와 해결, 검증 범위를 설명합니다. 팀 전체 기능은 코드·PR 등 확인 가능한 근거와 함께 소개하며, 자동 테스트·운영 배포처럼 증거가 제한된 항목은 완료로 과장하지 않습니다.

팀원별 역할과 GitHub 프로필은 저장소 README의 [Team 섹션](../README.md#-team)을 참고합니다. 커밋 이력은 변경 내역의 참고 자료이며, 작성자 표기만으로 협업 과정 전체를 단정하지 않습니다.
